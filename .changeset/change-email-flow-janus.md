`auth.<type>.changeEmail` moves a user to a new, proved e-mail address. `send(user, email)` validates the address as `update` would (`USER_INVALID`), issues a link's token for it — answered as `{ token, email, expiresAt }`, `email` being the new address to send it to — and spends the user's earlier links; `confirm(token)` moves the user there, marks it verified and keeps the password, the second factor and the sessions. Whether another user holds the address is not asked at `send` (it would tell who has an account): `confirm` answers `LOGIN_TAKEN` from the store's own constraint, with the token already spent. An `update` that moves the e-mail spends the pending links (`TOKEN_SPENT`), so moving back revives none; a link whose address was changed outside janus is `TOKEN_STALE`. `send` is throttled per user and per new address (`MAIL_THROTTLED`), a link lives `'1h'` (`tokens.changeEmail`), and `confirm` sends `user.emailChanged` with `formerEmail` — so the former address can be told — then `user.emailVerified`.

**Run the adapter's change first**: the `changeEmail` token kind needs janus-drizzle's migration (0.8) and janus-mongo's `syncMongoAdapter` (0.9), or every `send` is `STORE_FAILED`. **Gate `send`** behind a fresh sign-in (`assertFresh`) or a step-up: whoever changes the e-mail takes over password resets. Confirm from a `POST`, never from the link's `GET`. Documented in the e-mail flows guide, with a Hono route.
