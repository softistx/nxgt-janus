An instance with several user types now answers `verifyEmail.confirm(token)` and `resetPassword.confirm(token, password)` at its root, for the page a verification or reset link opens when it does not know the user's type, as it already does for `changeEmail.confirm`. The token is spent, the user is found by id whatever their type, and the link is confirmed under that type: the same write, events and refusals as the type's own `confirm`, with the user answered typed as the union of the types that can (`verifyEmail`: those with an e-mail; `resetPassword`: those with a password and an e-mail). `send`, `proveFirst`, `request` and `prepare` stay on each type. A type's own `confirm` is unchanged: a token issued to a user of another type is `TOKEN_UNKNOWN` there, and it is spent, so with several types an anonymous page calls the root one. **The root reset checks the password against the strictest `minLength`** of the types that have a password and an e-mail, before it spends the link: a refused password never costs the visitor their link, and a type with a more lenient rule sees the stricter one at the root only. `PASSWORD_TOO_SHORT` there reports that `minLength` and the `userType` that set it. A user type may no longer be named `verifyEmail` or `resetPassword`. The new `AnyTypeVerifyEmailApi` and `AnyTypeResetPasswordApi` type the root methods.
